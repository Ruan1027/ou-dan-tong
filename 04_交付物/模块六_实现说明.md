# 瓯单通 · 实现说明文档

> 赛道：2026 第六届 INTERCITY HACK 温州站 · 瓯客松｜「AI＋企业智能体」
> 选题：方向 07 碎片化沟通中的订单与任务协同
> 形态：寄生微信群的订单协同智能体（可体验网页版）
> 配套代码：`02_智能体代码/ou_dan_tong/`

---

## 一、项目概述

温州中小制造 / 贸易企业的订单与任务，大量散落在微信群、口头语音、截图里，没有结构化台账，业务员一忙就漏单、跟错状态、对不上交期。

**瓯单通**把微信群里的碎片化沟通，自动变成一份**实时、可查询、可提醒**的订单 / 任务协同台账：

- 把一段业务群聊贴进来，自动抽出订单与待办任务、登记入账；
- 随口问「万博那单到哪了」，立刻回当前状态、数量、交期，并附原文依据；
- 一句「出今日简报」，汇总新增、待报价、临期、逾期任务；
- 对**异常（负数 / 倒挂 / 格式错）、冲突（与在途单矛盾）、缺失（缺数量 / 交期）**三类棘手情形做显式识别与拦截，而不是静默写错。

整套逻辑用**零依赖 Python 原型**实现，逻辑 / 提示词 / 校验规则 / 数据模型与方案完全一致；用本地 JSON 文件替代外部数据库、用 DeepSeek（OpenAI 兼容）API 替代平台 LLM 节点，因此可在 WorkBuddy 中直接运行、演示、交付，无需任何外部服务。

### 2.2 技术选型

| 维度 | 选择 | 原因 |
|---|---|---|
| 语言 | Python 3.13（仅标准库） | 零第三方依赖，WorkBuddy 内 `python web_app.py` 即起，评委零安装 |
| Web | `http.server` 标准库 | 不引入 Flask / FastAPI，避免依赖与安装失败 |
| 存储 | 本地 JSON 文件（原子写盘） | 替代外部数据库，演示数据可截图、可备份、可还原 |
| 模型 | DeepSeek（OpenAI 兼容），未配 Key 自动 Mock | 真实模式可抽任意群聊；模拟模式免费演示全链路 |
| 契约 | `contracts.py` 单一真相源 | 多模块并行开发不漂移，所有字段定义集中一处 |

### 2.3 三种运行模式（同一份代码，平滑切换）

| 模式 | 触发条件 | 行为 | 用途 |
|---|---|---|---|
| 模拟模式 | 未设置任何 API Key | 用预置场景数据演示完整流程，输入不真实解析 | 评委 / 队友零配置体验 |
| 真实模式 | 设置 `DEEPSEEK_API_KEY` 或 `OPENAI_*`（任意 OpenAI 兼容端点） | LLM 真实抽取任意群聊 | 实际业务接入 |
| 口语化播报 | `OU_COLLOQUIAL=1`（叠加在上两种之上） | 查询/简报结果再经一次 LLM 改写成人话 | 需要展示「人话播报」时按需开启 |

切换对用户透明：未配 Key 时聊天区自动追加「⚠️ 模拟模式」提示，配好 Key 即消失。

> **口语化为什么默认关闭**：模板话术（`card_text`/`query_text`/`briefing_text`）本身就是人话，再经一次 LLM 改写会多花 8~9 秒，并会把「未命中具体客户/产品/状态」这类固定话术换掉，导致「问题—答案一一对应」失效。默认直出模板，既快又不失真；要演示口语化能力再显式开 `OU_COLLOQUIAL=1`。

## 三、核心模块

代码位于 `02_智能体代码/ou_dan_tong/`，按「契约先行、模块解耦」组织，队友 A/B/C/D 各自维护一个模块但统一 `import` 同一份契约。

### 3.1 模块地图

| 文件 | 模块归属 | 职责 |
|---|---|---|
| `contracts.py` | 模块二·1 | **契约单一真相源**：Message / ChangeSegment / 订单·任务记录 / ValidationResult 四类契约；状态机 `STATUS_ORDER`、`CHANGE_VERBS` 等常量 |
| `validator.py` | 模块二·7/8/9 | 确定性校验 + 变更比对：`classify_order` 四级判定、`classify_task`、`apply_change`、`validate_extraction` |
| `store.py` | 模块三 1~5 | JSON 台账存储、状态机流转、变更履历、一致性校验与修复 |
| `extractor.py` | 模块一 | LLM 结构化抽取（支持 mock 直出） |
| `llm.py` | 公共 | 极简 OpenAI 兼容调用，仅用 `urllib` |
| `prompts.py` | 模块一 / 四 | 抽取系统提示词、卡片 / 查询 / 简报文案（复用 `contracts.STATUS_ORDER`） |
| `agent.py` | 编排层 | `parse_chat` / `query` / `briefing` + `handle_message` 意图路由 |
| `web_app.py` | 模块六 | 零依赖网页服务，托管 `static/index.html` 与三个 API |
| `main.py` | CLI | 命令行入口（reset / demo / query / briefing） |
| `runtime/orders.json`, `tasks.json` | 运行时 | 订单 / 任务台账落盘文件（自动生成） |

### 3.2 契约先行（`contracts.py`）—— 多模块协作的「地基」

所有模块统一 `import` 本文件，**不得在本文件之外自行定义同义结构**。只加字段、不改既有字段名 / 类型，任何改动走 PR 全员确认。

四类契约：

- **契约 1 `Message`**：聊天输入（群名 / 发言人 / 时间 / 原文）
- **契约 2 `ChangeSegment`**：抽取出的变更片段（实体 / 字段 / 旧值 / 新值 / 置信度 / `change_verb` 是否显式变更动词）
- **契约 3 订单 / 任务记录**：与 `store.py` 运行时形状对齐，含 `change_log` 变更履历
- **契约 4 `ValidationResult {status, message, patch}`**：校验结果，模块二的产出

核心常量（单一真相源）：

```python
# 状态机：单向流转 + 终态「已取消」
STATUS_ORDER   = ["沟通中","已报价","已确认","生产中","部分交付","已交付","已取消"]
TERMINAL_STATUSES = ("已取消",)
# 变更动词：出现即视为「主动更新」，不判为冲突
CHANGE_VERBS   = ("改","变更为","调成","加到","加","增到","减到","降到","退回", …)
```

### 3.3 校验与变更比对（`validator.py`）

模块二核心 `classify_order(o, existing, order_date)`：对一条抽取订单做**异常 → 冲突 → 缺失 → 正常**四级短路判定，返回契约 4 的 `ValidationResult`。

- `validate_extraction(raw)`：把 LLM 抽取结果类型规整，缺客户 / 产品则跳过并计数；
- `apply_change(existing, extracted)`：后值覆盖前值，仅覆盖本次有值字段，并生成一条变更履历。

### 3.4 台账与状态机（`store.py`）

对应模块三 1~5：

- **三·1 存储模型**：`orders.json` / `tasks.json`，每张单含最新状态 + `change_log` 历史变更；
- **三·2 最新状态解析**：`apply_latest` 后值覆盖前值；冲突 / 异常锁定的字段不自动覆盖，只能经 `confirm_update` 人工确认写入；状态回退一律拒绝；
- **三·3 持久化**：原子写盘（先写 `.tmp` 再 `os.replace`），损坏文件自动备份兜底；
- **三·4 一致性校验**：`integrity_check` + `repair` 扫描重复 ID / 缺失字段 / 非法状态 / 孤儿引用并尽量自动修复；
- **三·5 状态机**：`can_transition` / `next_statuses` 基于 `contracts.STATUS_ORDER`，单向流转、禁回退，「已取消」为终态（进入后不可再流转）。

### 3.5 编排层（`agent.py`）

统一入口 `handle_message(text, store, llm, mock)`，按意图路由：

- 命中简报词 → `briefing()`；
- 命中查询词 → `query()`；
- 否则 → `parse_chat()` 贴群聊抽取入库。

`query()` 实现查询解析增强：状态关键词映射、时间区间（今天 / 本周 / 最近 N 天）、多字段命中（客户 / 产品 / 规格）相关度排序、多命中澄清反问、变更履历追溯（问「改过啥」看 `changes[]`）。

`briefing()` 汇总：`query_orders(created_on=今天)` 新增、`status=沟通中` 待报价（取最急）、临期（交期 ≤ 今 +3 天）、逾期任务。

## 四、主要功能

| 功能 | 入口 / 触发词 | 行为 |
|---|---|---|
| **群聊提取入库** | 粘贴群聊文本 | `parse_chat` 抽取订单 / 任务 → 四级判定 → 建单 / 更新 / 占位 / 拦截，并回卡片 |
| **订单 / 任务查询** | 「XX 那单到哪了」「生产中」「本周」「改过啥」 | 命中客户 / 产品 / 状态 / 时间，相关度排序，附原文依据；多命中反问定位；历史追溯列变更履历 |
| **今日简报** | 「出今日简报」 | 聚合新增 / 待报价最急单 / 临期 / 逾期任务 |
| **异常拦截** | 负数 / 倒挂 / 格式错 | 直接拦截不写入，卡片 🔴 提示 |
| **冲突识别** | 与在途单数值矛盾且无变更动词 | 不覆盖，标记 `flags.conflict` 待人工确认，卡片 🟠 提示 |
| **缺失追问** | 新建单缺数量 / 交期 | 登记「待补充」占位单，卡片 🟡 追问，台账可见待补 |
| **任务派发回执** | 纯任务（无订单）信息齐全 | 每条任务生成可见回执卡片，避免静默 |

网页端采用**双页面**还原真实应用场景，把「客户沟通」与「平台查询」严格分置：

- **💬 微信沟通模拟页**：还原微信沟通场景。左侧「客户」气泡为客户发来的消息（白气泡），右侧「瓯单通」气泡为智能体自动提取结果（绿气泡）。下方 5 个按钮模拟客户发来 5 类消息——🆕 新建订单 / ✏️ 客户改数量 / 🟡 信息缺失 / ⚠️ 数据冲突 / ⛔ 异常拦截，点击即驱动提取；右侧实时回显档案台账。
- **📊 平台汇总页**：承载平台侧查询动作。含订单 / 任务台账全表、状态统计卡，以及「🔍 订单查询」输入框（示例：查万博那单 / 温州机电那单 / 本周有哪些单）与「📊 出今日简报」按钮；并附「重置台账」。

> 设计要点：客户**发出**的信息（新建 / 改数量 / 缺失 / 冲突 / 异常）归属沟通页；平台**主动查询**（查单 / 简报）归属汇总页，符合企业"微信/钉钉沟通 + 后台汇总"的真实分工。

## 五、关键实现逻辑

### 5.1 四级判定（异常 > 冲突 > 缺失 > 正常）

`validator.classify_order` 短路优先级：

1. **主键缺失** → MISSING（无法建单，跳过）；
2. **异常**（最高优先级，直接 block）：数量非整数 / 负数 / 量相差 >10 倍（疑似多打零，BUG-08）/ 交期格式错 / 交期早于下单日 → ABNORMAL，绝不写入；
3. **冲突**：与在途单同客户 + 产品、数值矛盾、且**无显式变更动词** → CONFLICT，不覆盖，`flags.conflict` 待人工确认；
4. **缺失**：新建单缺数量 / 交期 → 登记「待补充」占位单 + 追问；
5. **正常**：带变更动词的更新 / 无矛盾新建 → `apply_change` 落库并留痕。

> 关键技巧：`CHANGE_VERBS` 区分「正常主动更新」与「矛盾断言」。例如「数量**改成** 6000」是更新（不冲突），而「交期 11-28」（台账 11-25，无动词）是冲突（不覆盖）。

### 5.2 状态机单向流转 + 终态

- 状态沿 `STATUS_ORDER` 单向推进，回退一律拒绝（`can_transition` 返回 False，除非 `force=True` 人工确认）；
- 「已取消」为**终态**：可从任一非「已交付」活跃态进入，进入后不可再流转；「已交付」后不可取消；
- `PLACEHOLDER_STATUS = "待补充"` 是缺失信息时的临时态，补全后可进入任意合法状态，不参与状态机比对。

### 5.3 变更履历 + 防幻觉

- 每次写入都向 `change_log`（与 `changes` 同一列表，互为镜像）追加 `{time, field, old, new, source}` 一条，用户问「改过啥」可回溯；
- **所有回复带 `source_excerpt` 原文依据**，查询 / 简报数字全部来自台账查询，LLM 不编数；
- 口语化改写（`_colloquialize`）后做 `_check_facts` 事实保全校验（数字 / 日期 / 状态值集合不得增删），失真即回退原文，杜绝"嘴上说五千、台账没改"类幻觉。

### 5.4 Mock 兜底与平滑切换

- 未配 Key 时 `web_app.py` 启动即 `seed` 两条在途单（温州机电法兰盘、王工 NMX-60），使冲突 / 更新 / 异常示例能命中 `existing`；
- `USE_MOCK = not (有Key) or OU_DEMO_MODE`，演示模式与真实模式由环境变量完全解耦，代码路径一致，切换无副作用；
- LLM 调用失败时层层回退原文，绝不因模型故障拖垮查询。

### 5.5 缺陷治理

当前缺陷看板 **12 项全绿（未修复 0）**，覆盖 BUG-01~12 及残留项（缺失追问、数量暴涨拦截、任务期限时刻、状态机终态、纯任务回执等），回归用例 `REG-01`（Mock 重复入库幂等）通过。详见 `模块五_测试报告.md`。
